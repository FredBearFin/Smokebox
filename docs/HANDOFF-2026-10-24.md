## 1. Who and what

**Freddy** (GitHub `FredBearFin`) is building **SmokeBox**, a startup: a "kitchen coach" kitchen display system (KDS) for food trucks and small kitchens. It is meant to be:
- **A paid, account-based product.** A kitchen's whole setup belongs to an account, not a device. It is hosted on the company's server.
- **A coach, not just a ticket screen.** It tells cooks exactly what to do next, by voice and on screen, built for "dumb cooks", low literacy and noisy kitchens.
- **A whole-kitchen optimizer at its core.** It plans every ticket across every station, knowing how many fryer baskets, burners and grill spots exist.

The product is **in development: there are no real customers and no saved kitchens to protect.** Do not spend effort on backward compatibility with old saves. Freddy said this explicitly.

### How to work with Freddy (he was clear about all of these)
**Treat it as a startup, not a portfolio project.**
- No talk of deadlines or "this costs X days".
- Don't under-scope: it needs paid accounts, real servers and security.

**Be explicit about what he must do.** End every update with a **"What you need to do"** section: exact clicks and exact commands, or "Nothing".

**Server commands.**
- He types into the **Hetzner web console, which cannot paste**.
- Keep commands short and familiar. Never ask him for error codes.
- If something fails, ask for a photo of the screen.

**Never claim to be working while idle.**
- If you say "I'm building X", keep working in the same turn until it is done or truly blocked.
- If blocked, say so at once.

**Tests.**
- Don't run long suites after small changes.
- While building, run only the 5-second smoke test.
- Run long suites once, before opening a pull request, **in the background**, and say how long they take ("about 2 minutes").
- Long silences look like being stuck. Post short progress notes.

**Answers.**
- Plain words, deep and analytical, written out in full, no jargon dumps.
- US spelling. Grams and kg for food.

**Never use pre-filled answer choices** (the AskUserQuestion-style option chips). He hates them. Ask in plain text if you must ask.

**Use his user feedback smartly.**
- Reason from the code; don't re-run his exact steps as a reproduction when the cause can be found by reading.
- Don't fixate on menu data in audits. Dishes are never hard-coded: a real kitchen starts empty, and only the demo kitchen and an optional "Start from an example menu" button have sample dishes.

**He wants a "real computer science" stack, not a web-dev one.**
- The approved direction is a **Rust** engine and server.
- He asked "what the fuck is Rust" at the end. Explain it plainly: a fast systems language like C++, but memory-safe; it compiles to WebAssembly for the offline tablet and to native code for the server. It was chosen over C++.

## 4. Architecture today

**Tablet app**
- One self-contained file, `dist/smokebox.html` (about 3 MB).
- `tools/build.mjs` concatenates `src/css/*.css` and `src/js/*.js` in name order. Each JS file is try-wrapped and parse-checked, and `SB_BUILD` is injected.
- There is one global, `SB`.

**Engine** (`src/js/20-engine.js`, 4,505 lines)
- Pure and deterministic: `apply(state, type, payload, now)`, `tick`, `serialize`, `validateBackup`, invariants I1–I15, undo, learning, stock, safety gates, money.

**Rust kitchen planner (new)**
- **The crate:** `engine/` (`schedule.rs`, `model.rs`, `ffi.rs`), pinned toolchain 1.97.0.
- **The build:** `node tools/build-engine.mjs` builds it into `src/js/18-engine-wasm.js` (base64, 162 KB, reproducible).
- **The bridge:** `src/js/19-planner.js` (`SB.planner.start()`, `startSync()`, `plan()`).
- **Who uses it:**
  - `20-engine.js` `replanInto` re-plans every open ticket after each action when any station limit is set.
  - The app waits for the planner before booting (`99-boot.js`).
  - The servers (`server.mjs`, `cloud.mjs`) and `test/_load.mjs` start it synchronously.
- **New data:**
  - `settings.capacity` = `{stationId: 0..50}`.
  - menu `perSlot` (portions per basket).
  - On items:
    - `moved`: the start time differs from the ticket's own plan;
    - `held`: a full station delays it;
    - `freeAt`: for a due dish at a full station, when a slot frees.
  - Invariant I5 is relaxed for moved items.

**Store and sync** (`30-store.js`)
- localStorage, a transport interface, an outbox, `adoptState` replay.
- The hosted transport is `32-cloud.js` (EventSource plus POST, a heartbeat watchdog, "Not connected" after 8 s).

**Servers**
- `server/server.mjs`: the live one-kitchen hub, WAL.
- `server/cloud.mjs`: the hosted multi-kitchen prototype, not deployed.
  - `node:sqlite`, scrypt passwords, `sb_session` cookie, CSRF guard, lockout, per-kitchen action log stored before "ok", snapshots plus replay, SSE.
  - Tests: `test/cloud.test.mjs` and the two-device browser test `test/cloud.e2e.mjs`, which proved offline tickets sync with no loss or duplicates.

**Tests and tools**

| Command | What it runs | Time |
|---|---|---|
| `node tools/test.mjs` | Unit suite: 1,037 tests on Smokebox, 1,032 on deploy | about 2 min |
| `node tools/smoke.mjs` | Smoke test | about 5 s |
| `node tools/guide-walk.mjs` | Guide walk: 324 checks | about 4 min |
| `node tools/qa.mjs --only floor --no-report` | Board browser checks | about 5 min |
| `cargo test` in `engine/` | Rust tests: 8 | seconds |

- **Comment audit:** `node tools/comment-audit.mjs`. Every named function needs a comment of 6 or more words directly above it.
- **CI** (`.github/workflows/ci.yml`): build, then the dist drift check, then unit tests, then the comment audit.
- Playwright is available via `toolRequire('playwright')` from `tools/_deps.mjs`.
- In a fresh worktree, set `SMOKEBOX_TOOLS=/home/user/Smokebox` so acorn is found.

## 6. Decisions made

**Stack**
- Rust for the engine and the API server, with Postgres.
- Stripe for billing.
- Hetzner, with staging and production and automated deploys.
- TypeScript for the screens, gradually.
- The full approved platform plan is in section 8.

**Rejected:** the intern's C++/WASM scheduler (`scheduler.cpp`, `66-order-math-wasm.js`):
- a second source of truth;
- wrong ids, station names and states;
- overwritten by `66-order-math.js` (`SB.orderMath =`);
- a missing fallback function;
- JSON broken by quotes;
- fabricated "live output".

Kept from it: station capacity and basket size, both now built.

**Rejected:** a Python AI service ("the current voices are fine").

**Voices**
- Natural Kokoro voices were sampled (michael, adam, heart and emma, plus Spanish and French) and Freddy loved them.
- **Plan:** run them in the tablet's browser with `kokoro-js`.
  - The model is about 90 MB, downloaded once, then offline.
  - Voices: 28 English, 3 Spanish, 1 French (female only), 4 Hindi, 2 Italian, 3 Portuguese, 5 Japanese, 8 Mandarin.
  - Default: English with a British voice.
  - Each device picks its call-out language.
- **Not yet built.** Also wanted: the best British device voice as the automatic default.

**Languages:** the screen stays English. Call-outs in English, Spanish and French first (Hindi was also asked for). A native speaker checks the wording.

**Name:** "Kitchen Coach" is taken in this industry (FSGenius has an app of that name). Branding is deferred: "marketing stuff, later".

**Header:** Front counter stays visible on the board (Freddy asked for it), despite the audit suggesting it move.

## 8. Approved platform plan (summary)

| Layer | Choice |
|---|---|
| Kitchen engine | Rust (`engine/`), WebAssembly on the tablet (offline) and native on the server, deterministic |
| API server | Rust (axum, tokio, sqlx), single binary |
| Database | Postgres, every row scoped by `kitchen_id` |
| Tablet app | The existing web app, moved to TypeScript; installable as a PWA; offline outbox |
| Voices | Kokoro via `kokoro-js` in the browser; no voice server |
| Payments | Stripe Checkout, Billing, Customer Portal, webhooks; minimal PCI scope |
| Infrastructure | Hetzner staging and production, Caddy TLS, GitHub Actions CI/CD, infrastructure as code, backups, monitoring |

**Build order:**
1. Foundations.
2. The Rust engine. The planner is done; the full brain is next.
3. The Rust server and Postgres.
4. Billing.
5. Security and operations.
6. Voices and languages.
7. TypeScript.

**Still open for Freddy:** the domain, pricing, and managed or self-hosted Postgres.
